# Передача проекта команде и ИИ

Состояние на **2026-11-06**. Здесь указаны оставшиеся задачи, места изменений и критерии готовности. Предложения по реализации ниже ещё не являются написанным кодом. Этот документ не объявляет продукт готовым к эксплуатации.

## 1. Что продолжаем

Доделываем **Windows desktop-приложение ИИ-аватара деканата** по исходному плану. Студент нажимает начало разговора и задаёт вопросы голосом; вымышленный сотрудник деканата отвечает по подготовленной базе вуза. Веб-версия на 100 одновременных разговоров отложена пользователем. Миграцию в браузер сейчас не выполнять.

Перед изменениями прочитать:

1. [product-decisions.md](product-decisions.md) — согласованные требования.
2. [docs/implementation-backlog.md](docs/implementation-backlog.md) — порядок F-01–F-10.
3. [docs/progress.md](docs/progress.md) — реальные проверки и история.
4. [docs/protocol.md](docs/protocol.md) — HTTP/WS, состояния, звук и мимика.
5. [docs/knowledge-base-contract.md](docs/knowledge-base-contract.md) — формат данных вуза.
6. [docs/windows-distribution.md](docs/windows-distribution.md) и [docs/third-party.md](docs/third-party.md) — поставка, ограничения и лицензии.

В старых частях журналов сохранились записи «Unreal отсутствует» и «аватар не создан». Это история предыдущих этапов. Текущий статус проверять по сводкам, коду и `assets/manifest/`, не переносить старые ограничения в новый план автоматически.

## 4. Что нельзя сломать

- Ответы о вузе строятся только по переданным фактам; неизвестные сведения не выдумываются. При конфликте сообщать о расхождении. Произвольный парсинг PDF/Word/сайтов в исходный объём не входит.
- База заменяется только в даунтайме, без активного разговора. Ошибка импорта оставляет прежнюю базу рабочей.
- Слышимый звук воспроизводит только backend. ACE получает тот же PCM с громкостью **0**. Последовательность: `speech` → настоящий native `face_ready` → `playback_start`. Нельзя возвращать старт звука сразу по `speech`.
- Сохранять привязку к `session_id`/`turn_id`, отмену и отбрасывание поздних результатов. `FDecanatFaceRequest` устраняет реальный deadlock ACE; не возвращать синхронную отмену SDK в игровом потоке.
- При перебивании аватар остаётся стоять. При завершении, бездействии и недоступном лимите — садится. Известная исчерпанная квота не должна запускать вставание. Переход подтверждается после завершения клипа.
- Бездействие: **60 секунд ожидания + 15 секунд предупреждения**. Генерация и озвучка не считаются бездействием. После завершения очищаются экран и контекст предыдущего студента.
- Студенческие кнопки: «Начать разговор», «Завершить», «Источники». Не добавлять студенту настройки, текстовый редактор вопроса или доступ к ОС.
- Служебные операции защищены паролем. `Ctrl+Alt+A` только открывает вход сотрудника. Это не авторизация.
- Журнал хранит текст/источники и подтверждённый озвученный префикс **30 дней**. Исходный микрофонный звук не архивируется.
- API-fallback выключен по умолчанию. Не переключать пользователя на платную API-ветку без его настройки.
- Не копировать аккаунты, API-ключи, `.codex` или действующие профили в сборку/репозиторий. Не запрашивать пароли в чате.
- Сохранять Windows-исправления: UTF-8, передачу системных переменных Codex без учёта регистра, `features.view_image=false`, закрытие SQLite-дескрипторов, загрузку TTS через binary stream для путей с кириллицей.
- Не менять `full_product_ready` на `true` по факту компиляции или присутствия DLL. Пройденный тест должен иметь конкретный сценарий, среду и результат.

## 5. Следующая реализация: F-05 — настройка сотрудником

**Нужно:** сотрудник проходит шаги «пароль → база → провайдер → модели → устройства → готовность» без командной строки и ручного редактирования JSON.

**Где:** `DecanatPanel.*`, `server.py`, `security.py`, `config.py`, `cli.py`, `tools/installed_desktop.py`; повторно использовать загрузку базы, установку моделей и диагностику.

**Как выполнить:**

1. Спроектировать и реализовать состояния первичной настройки на backend; UI показывает эти состояния. Хранить прогресс без паролей/ключей в открытом виде. Прерывание установки или перезапуск не должны сбрасывать уже существующие пароль и базу.
2. Сначала решить bootstrap. Сейчас `cli serve` требует настроенный пароль, а development-entry автоматически создаёт пароль в `initial-password.txt` и импортирует пример базы. Это временный путь, не готовый wizard. Для обычного первого запуска нужен ограниченный setup-mode: создание первого пароля допускается только в неинициализированном профиле через локальный защищённый bootstrap, после создания повторная инициализация запрещается. Не добавлять анонимный сброс существующего пароля. Точный новый API-контракт описать и покрыть отрицательными тестами до подключения UI.
3. После первоначального входа использовать существующие `/v1/admin/settings`, `/knowledge`, `/diagnostics`, `/password`, `/api-key`. Новым служебным маршрутам сохранять IPC bearer и проверку служебного доступа. Нельзя ослаблять Origin/loopback-защиту ради wizard.
4. Показать проверку ZIP, понятные ошибки и подтверждение импорта. Рабочую базу готовит вуз. Пример из `examples/knowledge` подключать только в явно выбранной демонстрации; не объявлять его реальной базой и не подменять им существующую.
5. Для Codex предусмотреть вход владельца через штатную авторизацию. Для API — защищённое сохранение ключа и выбор модели. Не считать наличие `codex.exe` подтверждением входа или доступного лимита. Реальная проверка ответа выполняется явно, с понятным результатом.
6. Модели подключать по существующим SHA; скачивание/индексацию выполнять вне диалога. Учитывать отдельные `--data-dir`/`--model-dir`, права на каталоги установленного приложения и сохранность действующей конфигурации.
7. Для устройств использовать текущую инвентаризацию, затем проверку F-10. До её полноценного завершения не изображать неработающий тест как успешный.
8. Показывать причины неготовности и `restart_required`. Сохранить запрет нового разговора до необходимого перезапуска. Готовность должна учитывать базу/индекс, провайдера, речь/устройства и реального аватара; HTTP 200 или наличие файлов недостаточны. В текущем health поле `avatar_assets_verified` не является положительной приёмкой аватара.

**Проверить:** новый профиль; повторный запуск с существующими данными; закрытие на каждом шаге; неверный пароль; повреждённый ZIP/модель; отсутствие входа/сети; смена аудиоконфигурации; запрет студенческого старта до завершения. Сотрудник должен пройти весь сценарий в GUI. Отдельно проверить свежую установку, где ещё нет ни пароля, ни базы.

## 6. F-06 — восстановление после сбоев

**Сейчас:** launcher завершает связанные процессы, native-запускатель использует Windows Job Object. Автоматического восстановления нет; WS-клиент создаёт соединение при инициализации.

**Где:** `tools/launch.py`, `installer/windows/launcher.cpp`, `DecanatClient.*`, при необходимости `server.py`/`session.py`.

**Как выполнить:**

- Сделать один supervisor, с конечным числом попыток и задержкой; не создавать независимые циклы перезапуска в Python и C++. Числа попыток/окно ограничения — техническая настройка, их ещё надо выбрать и описать.
- Отличать штатное закрытие приложения/выключение ПК от аварии. Нажатие крестика не должно вызывать бесконечное повторное открытие.
- Перед новым запуском завершать процессы прежней попытки, включая дочерний Codex, звук и renderer. Job Object должен очищать потомков также при перезапусках внутри живого supervisor, а не только при выходе всего приложения.
- Сначала исключить вторую активную копию, затем работать с connection-файлом. Сейчас `launch.py` удаляет файл до запуска backend; нельзя позволить второй копии удалить параметры живого приложения.
- Новый backend получает новый IPC-токен. Проверить готовность, перечитать актуальные URL/токен на клиенте, сбросить старые служебные токены и создать пустую студенческую сессию. Не восстанавливать голос и историю предыдущего студента.
- При исчерпании попыток показать сотруднику понятное состояние и способ обслуживания. Не делать массовый `taskkill` всех Python/Unreal-процессов на ПК — управлять собственными PID/job.

**Проверить:** падение backend, renderer и supervisor; падение во время ответа/мимики; занятый порт; зависший запуск; несколько аварий подряд; штатный выход; отсутствие осиротевших процессов, старой озвучки и старого bearer после восстановления.

## 7. F-07 — киоск и автозапуск

**Где:** новая документация/скрипты развёртывания для фактической редакции Windows, текущие launcher и служебный интерфейс.

Сначала выяснить редакцию Windows и доступные средства ограниченной оболочки/учётной записи. Подготовить профиль, автозапуск, защищённое обслуживание и проверяемый способ возврата к прежним настройкам. Fullscreen сам по себе задачу не закрывает. Политики ОС должны быть конкретными, проверяемыми и применяться владельцем стенда с нужными правами; не менять Explorer/политики рабочего ПК молча из скрипта разработки.

Учитывать, что текущий установщик и данные относятся к текущему Windows-пользователю. Установка сотруднику не делает автоматически приложение, базу и вход Codex доступными отдельному kiosk-пользователю. Спроектировать размещение runtime и профиля для выбранной учётной записи, не раздавая её секреты студентам.

**Проверить:** перезагрузка → готовое приложение; отсутствие доступа студента к ОС/настройкам; работа трёх разрешённых кнопок; вход сотрудника; штатное обслуживание и выход; восстановление после сбоя. Проверять на выбранной редакции ОС, а не обещать одинаковые политики для всех редакций.

## 8. F-08 — проверить и завершить видимый отсчёт

**Уточнение после чтения кода:** `Conversation.tick()` уже посылает меняющиеся `idle_warning.seconds`; `SDecanatPanel::Handle()` уже выводит это число. В прежней таблице статус был неточным. Основная задача — фактическая проверка и устранение найденных дефектов.

**Где:** `session.py`, `server.py` (housekeeping), `DecanatPanel.cpp`, при расширении snapshot — `contracts.py`/`docs/protocol.md`.

Проверить уменьшение числа в настоящем игровом UI, исчезновение при речи, завершение ровно по backend-дедлайну и очистку при новой сессии. Проверить округление первого числа и snapshot/reconnect: сейчас snapshot содержит `warning`, но не оставшиеся секунды. При необходимости добавить актуальное значение в snapshot. Не создавать второй независимый таймер завершения в Unreal.

**Приёмка:** управляемые часы подтверждают 60+15 секунд, генерация/озвучка не расходуют ожидание; UI действительно меняет число и не переносит предупреждение следующему студенту. Зафиксировать результат игрового прогона; по наличию обработчика пункт не закрывать.

## 9. F-09 — просмотр журнала

**Сейчас:** `Journal.list(limit, offset)` и защищённый `GET /v1/admin/journal` с этими параметрами уже есть; таблица хранит вопрос, ответ, источники, провайдера, версию базы, `spoken_text` и `interrupted`. UI показывает ограниченный список.

**Где:** `journal.py`, `server.py`, `DecanatPanel.*`.

Добавить UI-навигацию по страницам и открытие записи с подробностями. Для просмотра за период при необходимости расширить API фильтрами дат и метаданными страницы. Сортировка должна быть стабильной, параметры SQL — связанными, размер ответа — ограниченным. В подробностях использовать сохранённые снимки источников и подтверждённый озвученный префикс; повторный поиск в новой базе не заменяет источник старого ответа.

**Проверить:** несколько страниц, одинаковые timestamps, пустой период, удаление старых записей после 30 дней, перебитая реплика, отказ без служебного входа, очистка экрана после logout. Не добавлять хранение аудио и не менять срок на бессрочный.

## 10. F-10 — удобный звук

**Сейчас:** `device_inventory()` и `/v1/admin/diagnostics` перечисляют устройства без записи; есть стабильное поле `selection`. При пустом выборе используется системный вариант, на этом ПК проверен WASAPI. Ручной выбор не должен перезаписываться автоматическим.

**Где:** `audio_device.py`, `server.py`, `config.py`, `DecanatPanel.*`, `tests/test_audio_device.py`.

Добавить списки входа/выхода, обновление списка, явный тест микрофона с индикатором и тестовую озвучку. Отображаемые подписи отделить от сохраняемого идентификатора; не считать номер PortAudio постоянным после переподключения. Тесты доступны сотруднику вне диалога, прекращаются по отмене/выходу и не сохраняют микрофонное аудио. Не открывать конкурирующие потоки поверх активного AudioDeviceAgent: согласовать тестовый режим и освобождение устройства.

Отключение устройства должно снимать готовность и выдавать понятное действие. Если для изменений нужен перезапуск, показать это и выполнить его контролируемо с помощью F-06.

**Проверить:** отсутствие устройств; две одинаковые подписи; смена системного устройства; отключение/возврат USB-микрофона; отмена теста; правильный слышимый выход; AEC-reference от единственного проигрывателя; невозможность запуска теста студентом.

## 12. Как продолжить на стенде и не занять ещё 90 ГБ

Исходная рабочая папка: `C:\Games\AI-decanat`. Проверенный стенд: Windows 11 Pro, Ryzen 5 3600, 16 GiB RAM, RTX 3080 10 GiB, UE **5.6.1** в `C:\Games\UE_5.6`. Предпочтительный MSVC — 14.38, SDK 22621. Не подменять UE на 5.8 без отдельной проверки совместимости. Максимум параллельных задач сборки — 2; для Editor использовался core limit 4. Это параметры данного стенда, не минимальные требования продукта.

Последние изменения **не закоммичены**. Сначала посмотреть `git status`/diff, сохранить перенесённые изменения с Mac. Не применять reset/clean/stash как способ «починить окружение».

На этом ПК сохранены:

- исходники, `desktop/Decanat/Content`, `assets/source` и утверждённые образцы;
- `.runtime/unreal/package-with-ace/Windows/Decanat/Binaries/Win64/Decanat.exe` — рабочая сборка;
- `dist/installer-development-f04-05/` — проверенный EXE и **все 8 BIN-частей**, около 11 ГБ;
- локальные модели, vendor plugins и инструменты; данные профилей не удалены.

После очистки намеренно отсутствуют `dist/windows-development-f04-01`, старые установщики, сборка без ACE, Intermediate/staging/cooked и `.cache/ace`. Это пересоздаваемые копии, не пропавшие исходники. Освобождено 54.11 ГБ. Удаление Intermediate означает, что первая следующая C++-сборка заново создаст свой кеш.

**Дисковый режим:** одна актуальная рабочая сборка и один проверенный installer. Не делать полный payload/installer для каждого изменения UI или Python. Перед нужным packaging оценить временный объём, после успешной проверки убрать прошлые варианты и временные копии. Не распаковывать все варианты лицевых моделей. Перед удалением на Windows проверить абсолютный путь и отсутствие выхода через junction; сохранять исходники, Content, модели, автосохранения, настройки и базы.

При переносе команде передать незакоммиченные исходники и настоящие Content/ассеты отдельно от секретов. `.tools`, `.venv`, `.runtime`, `models`, vendor plugins и `dist` игнорируются Git; один clone не восстановит их автоматически. Пользоваться manifest/SHA и официальными источниками. Чужие аккаунты и целые пользовательские профили не передавать.

## 13. Проверки при разработке

Из корня проекта, для полного Windows-прогона — в окружении MSVC:

```powershell
& .venv/Scripts/python.exe -m pytest -q -rs --tb=short
& .venv/Scripts/ruff.exe check .
```

При восстановлении зависимостей использовать `uv sync --frozen --extra speech --extra models`; не обновлять lockfile без причины. На новом стенде нельзя объявлять пропущенные native/модельные проверки пройденными.

Для C++-изменений сначала целевая сборка, затем затронутый runtime-сценарий:

```powershell
powershell -NoProfile -ExecutionPolicy Bypass -File tools/unreal.ps1 -Action Build -WithACE -MaxParallelActions 2
```

Это сборка Editor, не обновление готового игрового EXE. Для проверки изменённого клиента/контроллера нужен соответствующий PIE или новый Game target. Полный cook/package выполнять только когда нужен актуальный игровой артефакт для интеграционного прогона. Команды packaging и модели — в `docs/windows-distribution.md`; инструменты лица — в `docs/avatar-authoring.md`.

`tools/verify_packaged_motion.py` покрывает управляемые сценарии состояний/IPC; `--real-face --play-output --cancel-preparation` требует настоящего ACE и воспроизводит голос через выход, микрофон не открывает. `tools/verify_windows_installer.py` действительно устанавливает и удаляет тестовую копию. Не запускать тяжёлые/GPU/акустические проверки поверх активного пользовательского разговора. Перед физической записью ясно обозначить её назначение; исходный звук не архивировать.

После каждого пункта обновлять backlog/progress и относящиеся к нему контракты. В отчёте разделять: написано, собрано, фактически проверено, требует внешнего доступа/стенда. Указывать точные команды и границы; не подменять приёмку числом Python-тестов.
